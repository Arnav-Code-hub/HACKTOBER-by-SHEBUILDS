# Migrations

**Alembic, centralised, single head.** `services/api/app/migrations/`.

Models live per-module (`app/modules/<m>/models.py`) but migrations do not.
Foreign keys cross module boundaries constantly here — a project references a
problem statement which references a cluster which references a district — and
per-module histories cannot be ordered against each other.

## Rules

- **The API owns the schema. Nothing else writes DDL.** The AI service is
  stateless; if it ever needs read access it gets the `janmaang_readonly` role,
  never the API's credentials.
- **Indexes go in migrations**, never applied by hand in psql. An untracked index
  is the classic "fast on my laptop, times out in the demo" bug.
- **Extensions only** in `infrastructure/docker/postgres/init.sql`. A table
  created there exists locally and is missing in production.
- **Review every autogenerated migration.** Alembic will happily emit a
  `DROP COLUMN` from a model you were still editing.
- **Prefer additive.** Add a column, backfill, drop it in a later release. A
  destructive migration cannot be rolled back by redeploying.

## Commands

```bash
make migration name="add priority score breakdown"   # create
make migrate                                          # apply
make reset-db                                         # nuke, migrate, reseed (local only)
```

CI applies every migration to an empty database on each PR, so a migration that
only works against *your* database fails before merge.

## Seeds

- `services/api/seeds/reference/` — real, committed, deterministic UUIDs,
  idempotent, production-safe. Geography and departments.
- `services/api/seeds/demo/` — the SIH dataset. **Every record carries a
  provenance label**, per [`docs/SOURCES.md`](../SOURCES.md). Never in production.
